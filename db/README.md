# База данных АвтоЗвук

Схема рассчитана на один магазин, PostgreSQL 17, валюту KZT и целые единицы товара.
Деньги хранятся в `numeric(19,2)`, ставки — в `numeric(5,4)`, время — в `timestamptz`.
Дневные отчеты нужно группировать в часовом поясе `Asia/Qyzylorda`, а не по дате UTC.

## Что находится в проекте

- `src/main/resources/db/migration/V1__initial_schema.sql` — таблицы, связи, индексы и представления.
- `V2__ledger_guards.sql` — неизменяемые журналы, защита партий и остатков.
- `V3__document_posting.sql` — проверки проведения документов.
- `V4__request_fingerprints.sql` — ключи и отпечатки запросов API для защиты от повторных операций.
- `V5__finance_request_keys.sql` — идемпотентность расходов, выплат и ручных корректировок бонусов.
- `db/tests/accounting_smoke.sql` — сценарий учета с проверками и откатом тестовых данных.
- `db/check.ps1` — проверка всех миграций в отдельном временном Docker-контейнере без открытого порта.

Миграции применяет Flyway при запуске backend. Hibernate только проверяет схему
(`ddl-auto=validate`). После применения миграции ее не редактируют: изменения добавляют новой миграцией.
Драйвер PostgreSQL и PostgreSQL-модуль Flyway добавлены в Gradle.

## Локальный запуск

В PowerShell из корня проекта:

```powershell
$env:DB_PASSWORD = 'укажите-свой-локальный-пароль'
docker compose up -d db
```

Backend использует `DB_URL` (по умолчанию `jdbc:postgresql://localhost:5432/avtozvuk`),
`DB_USER` (по умолчанию `avtozvuk`) и обязательный `DB_PASSWORD`.
Переменные задаются в окружении процесса или в конфигурации запуска IDE.
Файл `.env` читает Docker Compose, но Spring Boot сам его не загружает.
Не храните реальные пароли в репозитории.

Проверка SQL независимо от Java и Gradle:

```powershell
powershell -ExecutionPolicy Bypass -File .\db\check.ps1
```

Скрипт создает отдельную базу в контейнере со случайным именем и удаляет контейнер после проверки.
Рабочую базу он не использует. Проверяет SQL PostgreSQL, но не работу Flyway/Spring Boot.
В существующем проекте оставлена Java 21 из `build.gradle`; переход на заявленную Java 17
нужно согласовать с версией Spring Boot на этапе backend.

## Модель

| Область | Таблицы и назначение |
|---|---|
| Каталог | `products`, `categories`, `suppliers`; цена продажи находится в карточке товара |
| Доступ | `employees`, `app_users`; сотрудник и учетная запись разделены, роли OWNER/SELLER |
| Поступления | `purchases`, `purchase_items`; закупочная цена хранится у каждой позиции |
| Склад | `stock_lots`, `stock_movements`, `stock_adjustments`; партии, движения, причины корректировок |
| Продажи | `sales`, `sale_items`; продавец, ставка бонуса, снимки названия/артикула/цены |
| Возвраты | `sale_returns`, `return_items`; связь с конкретной позицией исходной продажи |
| Деньги | `payments`; отдельные положительные суммы CASH/KASPI_PAY, продажа или возврат |
| Расходы | `expense_categories`, `expenses`; отдельно от закупочной себестоимости |
| Сотрудники | `bonus_entries`, `salary_payments`; начисления, корректировки и реальные выплаты |
| История | `audit_log`; пользователь, действие, объект, прежние/новые данные, причина |

Удаление по внешним ключам не каскадное. Товары, сотрудники и учетные записи
отключаются через `active`. Аккаунтов и паролей по умолчанию нет.

## Принятые правила

**Склад и себестоимость.** Выбран FIFO. Новая поставка создает новую партию с собственной
закупочной ценой. Начальные остатки и излишки инвентаризации также создаются как партии
с известной себестоимостью и ссылкой на корректировку. Начальный остаток партии равен нулю;
только вставка движения меняет `quantity_remaining`. Отрицательный остаток запрещен.
Для продажи партия выбирается по `received_at, id`; одна позиция может списываться из нескольких партий.
FIFO выбирает backend; база проверяет количество и достаточность остатков.

Остатки и стоимость запасов доступны через `product_stock`. В карточке товара нет отдельного
редактируемого остатка или единой закупочной цены. `updated_at` товара должен обновлять backend.

**Продажи.** `discount_amount` — общая скидка на всю позицию, а не на одну штуку.
`line_total = quantity * unit_price - discount_amount`. Общая сумма документа — сумма позиций;
ее не дублируем отдельным изменяемым полем. Нулевая итоговая сумма допустима: платежей нет,
начисление бонуса равно нулю. Продажи в долг в первой версии не предусмотрены.
Оплата несколькими способами — несколько записей `payments`.
`request_key` продажи/возврата — UUID для защиты от повторной отправки запроса.

**Проведение.** Документ начинается с DRAFT. Перед переходом в POSTED база проверяет наличие
позиций, полноту движений, сумму оплат и наличие бонуса. Проведенные документы и их позиции
неизменяемы. CANCELLED используется только для непроведенных черновиков. Проведенная продажа
отменяется полным возвратом; статус исходной продажи остается POSTED, возврат хранится отдельно.

**Возвраты.** Частичные возвраты разрешены. Возврат на склад ссылается на исходное движение
продажи и восстанавливает ту же партию с прежней себестоимостью. Если позиция списывалась
из нескольких партий, возврат разбивается на несколько движений. `restock=false` означает,
что товар непригоден к продаже: остаток не увеличивается, себестоимость не восстанавливается.
База ограничивает суммарное возвращенное количество и сумму по исходной позиции.

Backend рассчитывает сумму частичного возврата пропорционально исходной цене после скидки;
последний возврат забирает оставшиеся копейки. База ограничивает общий максимум, но сама
не рассчитывает пропорцию скидки.

**Бонусы.** Текущая ставка сотрудника (по умолчанию 0.0500) копируется в продажу при создании. Изменение ставки сотрудника
не меняет историю. Начисление равно `round(сумма продажи * ставка, 2)`.
Возврат создает отрицательную запись прежнему продавцу; ручная корректировка требует причины.
Для исключения накопления ошибок округления корректировка возврата рассчитывается как
разность бонуса на оставшуюся выручку после и до текущего возврата. Например, при возврате
190 из 380 и ставке 5% корректировка составляет -9.50.
Проверка ставки/продавца начисления продажи есть в БД; расчет и проверка величины корректировки
возврата остаются обязанностью backend.

`employee_bonus_balances` показывает начисления, выплаченные бонусы и долг.
Отрицательный баланс после возврата уже выплаченного бонуса допустим и переносится вперед.
Выплаты зарплаты с типом SALARY не уменьшают баланс бонусов. Выплаты сотрудникам не нужно
повторно записывать в `expenses`, иначе расходы задвоятся.

**Исправления.** Склад, оплаты, бонусы, выплаты, расходы и аудит — журналы без UPDATE/DELETE.
Ошибочный расход или выплату отменяет новая запись с `reversal_of_id`, той же суммой
и причиной. Повторная отмена и отмена отмены запрещены. Исправленный расход/выплата — новая запись.
Для финансового итога сумма записи-отмены учитывается со знаком минус.

## Контракт backend

Транзакционные сервисы поступлений, продаж, возвратов и начальных остатков реализованы.
Ниже правила, которые также должны соблюдать будущие операции:

1. Каждая операция проводится одной `@Transactional` транзакцией: документ, позиции,
   движения, оплаты, бонус, аудит, затем статус POSTED. При ошибке откатывается все.
   Черновик можно сохранить **только без журналов учета**. Отложенные ограничения БД запрещают
   коммит журналов непроведенного документа. Движения меняют остаток внутри текущей транзакции.
2. Блокировать документ и позиции до записи журналов. Для нескольких товаров/партий брать
   блокировки в одном порядке (`product_id`, затем FIFO-партии); использовать `SELECT ... FOR UPDATE`.
   Обрабатывать deadlock/конфликт повторным выполнением всей транзакции с тем же request_key.
3. При возврате первым блокировать исходную продажу; затем документ возврата, партии и позиции.
   Проверять исходную скидку, округление возврата, ставку и суммарную коррекцию бонусов.
4. Не менять позиции после создания их движений даже в DRAFT. Не создавать неоприходованные
   партии вне транзакции поступления. Для корректировки остатков проверять права владельца.
5. Записывать `audit_log` в той же транзакции; не сохранять пароли/хеши/секреты в JSON аудита.
   Текущие сервисы записывают аудит; для изменения реквизитов товара сохраняются снимки до/после.
6. Проверять OWNER/SELLER, активность пользователя и сотрудника; хешировать пароли современным
   алгоритмом. Это реализовано сервисами и Spring Security; пароли используют BCrypt.
7. В production разделить учетную запись миграций и учетную запись приложения. Приложению
   не выдавать DDL/TRUNCATE и права владельца таблиц; запретить прямые правки партий.
   Триггеры не защищают от администратора БД, который может их отключить.

## Финансовые отчеты

Учитывать только проведенные документы. Не соединять напрямую несколько наборов позиций,
платежей и движений перед суммированием: это размножит суммы; сначала агрегировать каждый набор.

- Продажи после скидок: сумма `sale_items.line_total` по дате `sales.sold_at`.
- Возвраты: сумма `return_items.refund_amount` по дате `sale_returns.returned_at`.
- Чистая выручка периода: продажи минус возвраты периода, в том числе по более ранним продажам.
- Себестоимость: количество списаний SALE × цена партии минус восстановленная стоимость RETURN.
- Валовая прибыль: чистая выручка минус чистая себестоимость.
- Расходы магазина: `expenses` с учетом знака отмены, отдельно от себестоимости.
- Выплаты персоналу: отдельный отчет `salary_payments` с учетом отмен; не смешивать
  начисленные бонусы и выплаты в одном показателе расходов.

В тестовом сценарии закупка 1 × 100 + 2 × 120 = 340, продажа двух штук за 380 после скидки,
себестоимость 220, валовая прибыль 160, бонус 19. После возврата одной штуки за 190
в исходную партию стоимостью 100: чистая выручка 190, себестоимость 120, валовая прибыль 70,
бонус 9.50. Денежный поток от закупок и прибыль — разные показатели.

## Резервные копии

Для рабочего сервера настроить ежедневный `pg_dump -Fc`, хранение копии вне сервера
и регулярное восстановление в отдельную тестовую базу через `pg_restore`.
Docker volume обеспечивает сохранность при пересоздании контейнера, но не является резервной копией.
Автоматическое расписание и production-доступы на этом этапе не настроены.

Технические основания: [ограничения PostgreSQL](https://www.postgresql.org/docs/17/ddl-constraints.html),
[PostgreSQL-модуль Flyway](https://documentation.red-gate.com/fd/postgresql-database-277579325.html).
